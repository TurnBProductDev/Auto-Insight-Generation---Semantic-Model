# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is the mirror of this file for other tools; keep the two in sync (only the title line differs).

## What this repo is

Four top-level pieces for turning a Power BI semantic model into AI-generated analysis:

- **`pbi_agent.py`** (repo root) — the original MVP: headless auth + a single DAX round-trip against the Power BI REST `executeQueries` API. This is where the authentication approach was proven. Still live: `Benchmark Test/` imports it directly.
- **`powerbi-summary-agent/`** — the full product: a LangGraph + LangChain multi-agent pipeline that inspects the model, auto-generates DAX (the user never writes any), executes it, and produces **two outputs in one run**: a descriptive summary (*what* the numbers are) and an investigative `insight_report.md` (*why* they look that way), generated by two branches running **concurrently**.
- **`fastapi_backend/`** — **currently a docstring and a data file only.** `app/__init__.py` describes three endpoints (`/kpi/insights`, `/kpi/alerts`, `/report/summary`) that **do not exist yet**; there is no FastAPI code and no FastAPI dependency in `requirements.txt`. The real content is `app/kpi_thresholds.json`.
- **`Benchmark Test/`** (note the space in the directory name) — `run_kpi_benchmark.py` executes the `kpi_thresholds.json` KPI set against the live model and writes `benchmark_results.json`. It reaches Power BI through **`pbi_agent.py`, bypassing the agent pipeline entirely**, and each KPI runs as its own isolated `EVALUATE` so one broken measure can't blank the rest.

**`powerbi-summary-agent/PHASE_ROADMAP.md` is the active work plan** — what Phases 1–3b delivered, the deferred Phase 4 spec, and the guardrails each phase must respect. Read it before starting cascade/memory work.

### The core invariant

Deterministic code detects, computes, fingerprints, filters, and validates. The LLM only **selects and phrases** from a pre-computed list. Every cap, budget, novelty decision, and impact number is enforced in Python — never trusted to a prompt. This now extends to prose (see the clarity gate under the synthesizer). When adding a feature, decide which half it belongs to first.

### The KPI threshold system

`fastapi_backend/app/kpi_thresholds.json` defines 8 named retail KPIs — Revenue / Volume / Footfall growth, ASP, ATV, UPT, Category Decline Breadth, At-Risk Revenue Concentration — each with `formula`, `dax`, `direction`, and red/amber/green `thresholds`. It is effectively a hand-authored **driver tree plus expectation baseline** for the working model.

- KPIs bind to **measure names, not raw columns**: the model's column names have already drifted between the Desktop file and the published dataset (`NET_SALE_VAL_CURRENT` vs `net_sale_val_current`/`_ly`; `CAT_TABLE.CATEGORY_NAME` exists locally but not in the published dataset). The measure name is the stable surface.
- **No pipeline node reads this file.** The driver tree it encodes is not available to `semantic_profiler`, the stat detector, or any LLM node — they still infer metric relationships from name-token matching. Wiring it in is an open opportunity, not existing behavior.

## Authentication — the load-bearing detail

Power BI auth is **headless MSAL with a persisted refresh-token cache**, not the PowerShell `Connect-PowerBIServiceAccount` flow. This matters: an earlier approach shelled out to PowerShell from Python and hung, because interactive login can't surface through a captured subprocess. Do not reintroduce subprocess-based interactive login.

- Token cache lives at **repo-root `.pbi_token_cache.json`** (contains a refresh token — gitignored, never commit).
- Both `pbi_agent.py` and `powerbi-summary-agent/src/tools/powerbi_executor.py` point at this **same** cache file (the executor resolves it via `parents[3]`), so the agent runs silently without a second browser login.
- `CLIENT_ID` is the well-known Azure PowerShell public client — needs no app registration. Tenant selection is configuration, not source code: `tenant_id` in the active `config.json`, overridden by `POWERBI_TENANT_ID`. First run ever opens a browser once; every run after is silent.
- **Two audiences, one cache.** `SCOPES` (`analysis.windows.net/powerbi`) drives `executeQueries`; `FABRIC_SCOPES` (`api.fabric.microsoft.com`) drives the measure-definition enrichment. Both are minted silently from the same refresh token — `get_fabric_token(allow_interactive=False)` returns `None` rather than launch a browser (enrichment is optional, must never hang an automated run). The two acquisitions are sequential inside Node 2 (pre-fork), so the unlocked-cache concurrency rule still holds.
- Requires the tenant's **Execute Queries** setting enabled and read/build permission on the dataset.
- **Concurrency rule:** `get_powerbi_token()` does an unlocked read-modify-write of the cache file — safe serially, unsafe from two branches at once. Node 2 fetches one token into `state["pbi_token"]` and both branches pass it to `execute_python(..., token=...)`. Never make a post-fork node call `get_powerbi_token()` directly.

## Agent architecture (`powerbi-summary-agent/`)

A LangGraph `StateGraph` over `SummaryAgentState` (a `total=False` TypedDict in `src/state.py`). After `understand_report` the graph **forks into two branches that run concurrently** (LangGraph runs independent nodes of a superstep on a thread pool — all node code is plain sync) and reconverge at `save_outputs`:

```
load_config → read_metadata → semantic_profile → baseline_scope
    → baseline_coverage → understand_report
    ├─→ plan_dax → generate_dax → validate_dax → execute_dax
    │       → normalize_results → summary_period_resolver
    │       → summary_candidate_builder → summary_novelty_filter
    │       → fresh_summary_generator → fresh_summary_validator
    │       → summary_branch_done ─┐
    └─→ insight_normalize → insight_temporal → insight_business_day_source
        → insight_recent_week → insight_daily → insight_evidence_catalog
        → insight_stat_detector → insight_novelty_filter → insight_signal_detector
        → insight_evidence_assembler → insight_gap_scan → insight_investigator
        → insight_synthesizer → insight_branch_done ─┴→ save_outputs → END
```

### Concurrency contract — read this before touching state or adding nodes

- `logs`/`errors` are **reducer-backed channels** (`Annotated[List[str], operator.add]`). `RunLogger` (`src/utils/logger.py`) therefore collects **only the current node's new lines** and `updates()` returns just that delta — LangGraph concatenates. Never seed a logger from prior state or return accumulated lists; that double-counts under the reducer. Every other state key is single-writer per superstep: a node in one branch must never write a key a node in the other branch writes.
- Shared `fatal` is written only pre-fork (`load_config`, `read_metadata`). Post-fork, `validate_dax` writes `summary_fatal`, whose router short-circuits only the summary branch; one branch failing never blocks the other output.
- **The join is a barrier, not loose edges.** Each branch (happy path *and* fatal short-circuit) funnels through its `*_branch_done` node; a joined edge `(["summary_branch_done", "insight_branch_done"] → save_outputs)` waits for both. The only other way into `save_outputs` is the single pre-fork fatal edge. Preserve this shape when rewiring — ad-hoc edges into `save_outputs` from mid-branch can fire it twice or race.
- Barrier nodes log `=== <branch> finished ===` — those timestamps in `run_log.txt` are how you confirm the branches actually overlapped.

### Summary branch

**Two summary implementations coexist, switched by `fresh_summary_enabled` (default true).** `_after_normalize` routes to `summary_period_resolver` (fresh) or the legacy `generate_summary`. Both land on `summary_branch_done`. When you touch the summary branch, check which path is live — the legacy node is still wired and still tested.

`summary_fatal` no longer short-circuits to the barrier in fresh mode: `_after_validation` sends it to `summary_period_resolver`, because the fresh chain can still write an honest descriptive view from the pre-fork baseline portfolio. Legacy mode keeps the old shortcut.

The fresh chain mirrors the insight branch's deterministic-before-LLM shape:

- `summary_period_resolver` — deterministic. Resolves the summary's own reporting period and freshness (delayed/stale) from summary results, baseline evidence, and metadata. **Deliberately does not read or mutate the insight branch's temporal gates** — the two are independent.
- `summary_candidate_builder` — deterministic. Builds the run's candidate *perspectives* (store / division / category / product / time / volume / transaction aspects) plus an authoritative `supported_facts` sheet with pre-formatted signed `display_value`s.
- `summary_novelty_filter` — deterministic. The summary's own cross-run memory gate (`summary_memory.py`, `summary_history.py`), mirroring the insight novelty filter with its own store, policy, and cooldown knobs (`summary_memory_*`).
- `fresh_summary_generator` — LLM, structured output. Emits `headline` + `metrics` tiles + exactly three sections (`What's working`, `Risks`, `Recommended actions`) + `covered_candidate_ids`. **Code injects each tile's display value and tone; the LLM only picks a `fact_id` and writes a label.** Recommended actions must open with a safe verb (Assess/Compare/Confirm/Investigate/Monitor/Prioritise/Review/Segment/Validate) — it may recommend checking, never prescribe pricing, staffing, or operational change.
- `fresh_summary_validator` + `src/tools/summary_validation.py` — deterministic evidence-grounding and shape checks, including per-section tone constraints (`what's working`→positive, `risks`→warning/critical, `recommended actions`→info). `summary_visual.py` renders the structured result.

- **LLM nodes** (`report_understanding`, `dax_planner`, `dax_generator`, `summary_generator`) call `get_llm(state, ...)`; the first two use `.with_structured_output(PydanticModel)`, the last two are free-form text (DAX and markdown).
- **Deterministic nodes** (`metadata_reader`, `dax_validator`, `result_normalizer`) — no LLM.
- `dax_planner` plans free-text `intent` strings; `dax_generator` is an LLM call per intent writing the `EVALUATE` DAX directly (this replaced an earlier fixed-template design — Node 5 is *not* deterministic).
- The **validator** (`dax_validator.validate_one`) regex-parses every `'Table'[Column]`/bare `[Measure]` token out of the DAX text and cross-checks against metadata. It is **alias-aware**: a quoted string in an argument slot (`ADDCOLUMNS(..., "Revenue", [SALES])`, same for `ROW`/`SELECTCOLUMNS`/`SUMMARIZECOLUMNS`) whitelists later bare `[Revenue]` references in that same query. Failed queries are kept as `skipped_dax_queries` for repair, not discarded.
- **Node 7 (`execute_dax` in `graph.py`) runs a one-shot repair loop** (`_run_with_repairs`, shared with the insight branch): validator-skipped queries and queries Power BI returned an embedded error for get fed to `dax_generator.repair()` once with the exact error text, re-validated, and re-run.

### Shared metadata scanner and insight branch

- `semantic_profiler` is deterministic. It uses metadata names, expressions, formats, descriptions, data types, hidden flags, and relationships to build coherent current/prior/change measure families, identify the main additive value metric and volume drivers, and rank entity/business/time dimensions. Production scan templates contain no model-specific table, column, measure, or member names.
- `baseline_scope` builds one metadata-derived entity query and classifies actual rows as comparable, current-only, prior-only, or inactive. Optional configured populations are machine-enforced business-rule overrides and are audited against this data-derived classification.
- `baseline_coverage` builds and executes the complete bounded diagnostic portfolio pre-fork. It is the single writer for broad scan state, and both branches reuse its evidence. Templates carry construction-time contracts; they are never LLM-repaired because a rewrite would invalidate provenance.
- `scope_validator` deterministically rejects every query using prior/change metrics unless the metadata-detected entity filter proves the resolved comparable population. It also rejects excluded/current-only members. Summary validation and repair, coverage, gap scans, and investigator probes all use this gate.
- `evidence_contract` catalogs grouping, metric bundle/phase/semantic role, population, filters, TOPN/truncation, completeness, and DAX hash. Construction-time hints are authoritative; legacy free-form artifacts use a conservative parser.

- `insight_temporal` — **deterministic, no LLM; the Phase 2 grain gate + temporal series.** Runs between `insight_normalize` and `insight_evidence_catalog`. It judges each candidate time axis and, if a **valid business time grain** exists, scans one comparable primary/volume series over it (appended to `insight_clean_data` so it flows through the catalog and stat detector). A date column can be a *load/posting* date, not business activity — on the working model `UPDATED_DATE` concentrates ~all revenue on month-end (a single bucket held 0.53 of the total), so the gate **rejects** it, **gates its trend table** (`insight_temporal_gated_tables`, so `trend()` won't mine month-end spikes), and falls back to the finest valid grain — here the clean `DOC_MONTH` 1..12 monthly series. If nothing is valid the level self-disables and the report carries a caveat (`insight_temporal_verdict`). Executes with the pre-fetched `state["pbi_token"]` (post-fork safe). See "Temporal (period) level" below.
- `insight_business_day_source` — **deterministic, no LLM; the shared Phase 3/3b capability + freshness gate.** Runs between `insight_temporal` and `insight_recent_week`. It owns the ONE REST fetch and all axis validation that both `insight_recent_week` (weekly/rolling folding) and `insight_daily` (daily incidents) need — pulling this out of `insight_recent_week` means disabling one consumer, or a folding-specific failure in one, never starves the other of the fetch it needs. It answers *"is there a genuine, current business-DAY axis?"*. It tries up to `insight_week_max_date_probes` metadata-ranked date dimensions (or validates the exact `insight_business_date_override`), rejecting: a **stale** axis (`(today − data_as_of).days > insight_week_max_data_lag_days` → the honest "data only available through …" caveat), a **batch/load** date (one bucket over `insight_temporal_batch_share`), a **non-additive** primary metric (metadata `additive_candidate` **and** a windowed reconciliation must both hold — the daily sum must equal a `CALCULATE` over the same date range), a **timestamped** axis (calendar-day grain required for the MVP), or sparse data. Runs if EITHER `insight_recent_week_enabled` or `insight_daily_enabled` is true. On success it scans one comparable **daily** series (`build_daily_series_scan`, CURRENT additive metrics only) and resolves `effective_data_as_of` — the true `data_as_of` rolled back to the previous *operating* day when it equals "business today" and `insight_daily_exclude_today` is set, so a still-loading current-day row never leaks into a rolling window or a daily incident's last day (calendar-week folding always keeps the TRUE `data_as_of` — trimming it would wrongly skip an already-complete preceding week). Writes `state["insight_business_day_source"]` (`{axis_key, axis_reference, value_alias, additive_aliases, rows, operating_days, data_as_of, effective_data_as_of}`) and `insight_business_day_verdict.json`; timezone is day-granularity only (`insight_business_timezone` `"auto"`/unsupported is rejected LOUDLY, never silently naive). Makes ≤ `2 × max_date_probes + 1` REST calls, all with the pre-fetched `state["pbi_token"]` (post-fork safe). **On the working model this gate DISABLES both consumers** — `UPDATED_DATE` is a batch date *and* the data is ~2.5 years stale — and says so.
- `insight_recent_week` — **deterministic, no LLM; folding only.** Runs between `insight_business_day_source` and `insight_daily`. Reads the already-validated `insight_business_day_source`; a folding-specific failure here (e.g. "insufficient complete weeks") disables only this node's own output, never the shared source. Folds the daily series **in Python** (never DAX `WEEKNUM`) per `insight_week_mode`: `"calendar"` (default) into Mon–Sun weeks (`fold_weeks`, using the TRUE `data_as_of` — a week is complete iff its Sunday ≤ `data_as_of` and it covers the learned `operating_days`, so missing weekends are fine but a Monday-only week is not); `"rolling"` into non-overlapping 7-day windows counting back from `effective_data_as_of` (`fold_rolling_windows`, `coverage_kind: "recent_week_rolling_history"` — structurally identical to `fold_weeks`, just anchored to "today" instead of the Monday boundary; NOT a 1-day slide, which would overlap 6/7 with its neighbor and both break the stat detector's non-overlapping week-over-week comparison and autocorrelate its z-score baseline). Appends the folded table to `insight_clean_data` and attaches a bounded target-vs-previous-window **driver** breakdown by the metadata primary dimension (`state["insight_recent_week_drivers"]`, the Phase-2 drill pattern; reused unchanged for rolling since `pick_target_window_rolling` returns the same shape as `pick_target_week`). Verdict + per-axis checks in `insight_recent_week_verdict.json` (now also carrying `window_mode`). See "Recent-week monitoring (Phase 3 / 3b rolling)" below.
- `insight_daily` — **deterministic, no LLM; the Phase 3b daily anomaly incidents node.** Runs between `insight_recent_week` and the evidence catalog, reading the SAME `insight_business_day_source` — independent of `insight_recent_week_enabled` and of whether weekly folding itself succeeded. `flag_abnormal_days` tests each day against a trailing rolling reference and (when `insight_daily_min_weekday_occurrences` prior points exist) the same weekday's own history, built up chronologically so a day's reference never includes itself or future data. Combining the two is **AND, not OR**: both must clear their own test (z-cutoff **and** materiality if the reference is variable; materiality alone if flat, since a flat reference's z is undefined) and agree in direction — this is what stops a systematic weekend low from being flagged (the trailing reference fires against a weekday-heavy mix, but the same-weekday reference correctly vetoes it). `merge_incidents` collapses consecutive same-direction abnormal days into ONE incident, treating a gap of only non-operating weekdays (a closed weekend) as adjacent — so a Friday+Monday dip bridging a closed Sat/Sun is one business incident, not two. A recency filter (reading the memory store's `daily_cursor`, no lock needed) is applied ONCE, here, before any row reaches the stat detector: eligible iff `episode_end > previous_cursor` (extends known territory) OR `episode_end >= effective_data_as_of - insight_daily_recent_days` (still recent) — on the very first run for an axis there is no `previous_cursor`, so only the second clause applies (no doubled window). Appends a `daily_incidents` table (never `window_complete: true` — it's an incident-derived, sparse table, not a full daily series) and writes `insight_daily_verdict.json` including `analysis_complete` (gates whether `commit_run` may advance the daily cursor).
- `insight_stat_detector` — **deterministic, no LLM.** Computes contribution-to-change bridges, top-N concentration, robust-z outliers, trend slope/change-points, reconciliation, entity lifecycle findings, the composite **`recent_week()`** movement (shared by the `recent_week_history` calendar table and the `recent_week_rolling_history` rolling table — one method, a `window_mode` field derived from which coverage_kind matched, not a duplicate), and (Phase 3b) **`daily()`** on the `daily_incidents` table. Metric roles and triples come from construction-time metadata contracts; numerical identity inference is only a legacy-artifact fallback. Additivity requires a complete comparable breakdown. It carries an exact revenue decomposition using `(Q1-Q0)*(R0/Q0)` for volume and `Q1*((R1/Q1)-(R0/Q0))` for rate; rate may include mix and is never automatically called pure price. Synonymous measures are collapsed so one story yields one candidate. `daily()` is dispatched **exclusively** for a `daily_incidents` table (never alongside `concentration`/`outliers`/etc, which could otherwise misread an incident row's numeric fields — `peak_z`, `cumulative_impact`, `day_count`, … — as a segment breakdown). When `window_mode == "rolling"`, `recent_week()` ALWAYS records a raw structured observation (`state["insight_rolling_observation"]`, no `story_key` — that's computed downstream, see below) regardless of whether the reading clears the significance gate, so memory can later learn a rolling incident recovered. The node never raises; on failure the signal detector can fall back to raw rows.
- `insight_novelty_filter` — **deterministic, no LLM; the cross-run memory gate (Phase 1).** Sits between the stat detector and the signal detector. It fingerprints every deterministic candidate with a stable **`story_key`** (`src/tools/insight_memory.py`), drops the ones already reported in earlier runs, tags each survivor with its temporal `level` (Phase 1: everything is `high`), caps eligible candidates per level, and emits `insight_eligible_candidates` (unseen only) plus `insight_novelty` (`{detected, suppressed, eligible, selected, policy, reason, memory_status, level_breakdown, resurfaced, rolling_unavailable}`). Filtering **before** the LLM is deliberate: post-filtering an LLM that returns known findings could leave zero signals while unused candidates remain. When `insight_memory_enabled` is false it is a transparent pass-through **except** for `recent_week_rolling` candidates, which are dropped outright even here (decision below). When the store reads **corrupt** it fails LOUD (skips suppression, emits everything, `reason=memory_corrupt`) and downstream commit is refused so the damaged store is preserved. Phase 3 adds the **`recent_week`** level (from a `recent_week_*` `coverage_kind`; the more specific `recent_week_rolling`/`daily` checks run first, since `"recent_week_rolling_history".startswith("recent_week")`), capped by `insight_candidates_weekly`. **Rolling-week (Phase 3b) gets its own eligibility path that NEVER consults `never_repeat`/`cooldown`**: pulled out of the normal candidate list before ordinary suppression runs; unknown story_key → eligible; known + an inactive→active transition (vs the stored `rolling_state`) → eligible; known + `insight_memory.resurface_check` fires (reversal / growth-multiple / rolling's own delta-pct drift) → eligible; otherwise suppressed — and dropped outright (never emitted raw) when memory is disabled or corrupt, since the level is structurally meaningless without persisted state. The rolling story_key is computed in exactly ONE place — here, via `_rolling_key` for the observation-only case (no candidate this run) — so a real candidate's key and the standalone observation's key can never drift apart; the resolved key is stamped onto `state["insight_rolling_observation"]` before `commit_run` reads it. See "Cross-run insight memory" and "Recent-week monitoring" below.
- `insight_signal_detector` — LLM structured output; **selects from the eligible candidates** (`insight_eligible_candidates` in memory mode, else the full stat list) copying their computed `impact_value`/`impact_share` rather than estimating, and flags findings ranked by **materiality** (size × share of total), each classified `kind: business | data_quality` and quantified (`impact_value`, `impact_share`, `affected_segment`) alongside its "why" question and evidencing scan query. **No cascade level (high/period/recent_week/recent_week_rolling/daily) gets priority ordering** — `_rank_and_cap` sorts every bound signal purely by its deterministic candidate's `score` (materiality) and takes the top `insight_max_new_per_run` (or `insight_max_signals` outside memory mode), with the DQ sub-cap (`insight_max_dq_signals`) enforced across the ranked list so reconciliation noise can't crowd out business findings. In **memory mode** binding is **exact-`candidate_id`-only** (a signal with no/unknown id is dropped — the segment heuristic is disabled so a suppressed story can't be mis-attached); a merged signal lists `related_candidate_ids` so every `covered_story_keys` entry is marked seen on commit. `_copy_candidate_facts` deterministically copies each bound candidate's computed facts (incl. `score`) — including the structured **`recent_week`** payload (week bounds, actual/previous/expected, WoW/rolling %, robust z, drivers, `window_mode`) and, for a `daily_incident`, `episode_start`/`episode_end`/`peak_z`/`day_count`/`actual_total`/`expected_total` — onto the signal, so the synthesizer/memory/API/tiles read structured values, never LLM prose. A rolling reading's `change_pct` is ALSO copied to a top-level `signal["change_pct"]` (the memory whitelist reads it there, not from the nested payload) — without this the rolling delta-pct resurface trigger has nothing to compare. `_backfill_uncovered` is a narrow backstop, not a priority mechanism: if a whole LEVEL has eligible material candidates but the LLM's response touched none of them, its single best candidate is injected so that level can never go silently invisible to LLM bias — it then competes on the same materiality score as everything else, never ahead of it. Outside memory mode the legacy `_bind_candidates` path is unchanged.
- `evidence_assembler` — deterministic reuse-before-DAX. It can quote a correctly scoped construction-time row from a partial tail, but only complete, reconciled, correctly scoped evidence can close a drill dimension. Partial or ambiguous evidence stays verification-required.
- `insight_gap_scan` — deterministic targeted DAX over metadata-compatible dimensions. Per-signal and global budgets bound REST latency; a DAX-hash cache is shared with the investigator. Multi-segment findings preserve exact member arrays and use multi-value `TREATAS`, never a comma-joined fake member.
- `insight_investigator` — **the only tool-calling agent.** Per signal it gets the brief, reusable evidence, gap results, and remaining budget. `run_dax` is object-validated and scope-validated, rows are capped, cached hits are free, and actual gap plus investigator REST calls cannot exceed `insight_max_investigation_rounds`. The normal adaptive investigator path is 0–3 fresh probes. Every success/rejection/budget refusal/failure/definition lookup is recorded; a forced plain-text turn closes an unconcluded trail.
- `insight_synthesizer` — free-form markdown over signals + trails, hedged contribution/correlation language enforced by prompt, **plus a deterministic manager-facing clarity gate.** `_clarity_issues` parses only the `# Key Insights` section (technical appendices stay auditable and are exempt) and rejects the report unless every finding paragraph: is ≤90 words, states at least one figure but no more than four, plainly says what changed, opens with a bold takeaway containing both a change word and a figure, names an evidenced contributor, ends with a specific check verb, and uses **none** of the analyst shorthand in `_TECHNICAL_MANAGER_PHRASES` (`volume effect`, `rate effect`, `share of total change`, `basket mix`, `sell-through`, `materiality`, `reconciliation`, `z-score`, `probe`, `signal`, `trail`, …). It also asserts the paragraph count equals the number of non-`data_quality` signals. On failure it feeds the specific issues back and re-invokes — **up to 3 LLM attempts per run**, then logs an error and ships the best attempt. This is prose subject to the same code-checks-the-LLM rule as numbers; the matching prompt guidance lives in `insight_synthesizer_prompt.md` and `fresh_summary_prompt.md`, and `scripts/replay_plain_language_output.py` covers it offline. Note the checks are regex-based: they reliably catch jargon and missing figures, but a well-formed empty sentence can still satisfy them. It also emits **`insight_tiles.html`** (via `src/tools/insight_tiles.py`, best-effort/never fatal, and **gated by `insight_tiles_enabled` which now defaults to `false`**): one visual tile per Key-Insights paragraph — bold heading + a data-driven inline-SVG chart + a native `<details>` "See more" holding the full paragraph. Paragraphs are matched to signals by a global best-score assignment (segment-in-heading beats a merely-cited share), and the chart is chosen **deterministically from each signal's OWN structured data** — price/volume decomposition → waterfall; breakdown rows (investigator probes, else the `evidence_query` scan table) → diverging bar with the subject segment highlighted; top-N concentration → donut; current-only → KPI + "not comparable" badge; floor fallback → KPI + share meter. No number is ever parsed from prose (prose supplies only heading + see-more text), so the board regenerates for any run's signals. Dependency-free (no JS/libs), light/dark aware, dataviz diverging blue↔red palette on the navy chrome.
- All metadata baseline, gap, and investigator execution uses the Python REST path and the single token fetched pre-fork. PowerShell mode applies to the summary branch only.

### Cross-run insight memory (Phase 1 — "unseen findings" mode)

`src/tools/insight_memory.py` gives the insight branch a memory so a **daily** run surfaces only findings it hasn't reported before. This is the memory + novelty layer; it does NOT yet add genuinely-new daily information (that is the deferred weekly/daily temporal work — the `level` field and per-level caps are scaffolding for it). Enabled by `insight_memory_enabled` (default true).

- **One authoritative store per dataset**: `insight_memory/<dataset_id>/memory.json` (gitignored), written as a single **atomic** transaction (temp file + `os.replace`, best-effort lock). Shape: `{schema_version, watermark, records{story_key→record}, journal{day→entries}}`. `daily_insights.md` is **derived** from it (regenerated each commit) and may safely lag.
- **`story_key`** is the stable suppression identity: a level-prefixed versioned SHA-256 of canonical JSON that **excludes mutable properties** (direction, impact, episode end) — so a later phase can re-alert on a reversal/growth without the key changing. High-level canon = `{level, dataset, scope, period_anchor, analysis_type, metric, dimension, segment}`; `metric` is the contract `metric_roles` bundle/family (not the drifting alias), `segment` is NFKC+casefold+sorted, `period_anchor` is the reporting-period bucket of the data watermark (so a new period resurfaces its stories). **Never** a candidate id (ranking-based numbering drifts).
- **Policy**: `insight_memory_policy` = `never_repeat` (default; suppress a reported story forever) or `cooldown` (resurface after `insight_memory_cooldown_days`) — for the `high`/`period`/`recent_week`/`daily` levels only; `recent_week_rolling` never consults this (see above).
- **`commit_run(state, reported_signals)`** (Phase 3b; replaced `commit()`) is the single call, once, in the post-join `save_outputs` barrier, gated on: memory enabled ∧ not `fatal` ∧ `memory_status != "corrupt"` — **not** on signals existing. "Observed" and "reported" are different things: the daily per-axis cursor (`memory["daily_cursor"]`, gated on `insight_daily_verdict.analysis_complete`, forward-only) and the rolling observation/activity snapshot (`memory["rolling_state"]`, from `state["insight_rolling_observation"]`, also forward-only) advance **unconditionally** whenever the underlying gate validated an axis this run, regardless of whether `reported_signals` is non-empty; the caller (`graph.py`) computes `reported = signals if state.get("insight_report") else []` so a synthesizer failure (only a stub report written) still lets observations advance but never marks a story "seen" that the user never received. Only when `reported_signals` is non-empty does it also record signals, marking **all** `covered_story_keys` (primary + merged) seen, **merge** `journal[today]` by story_key (a 2nd same-day run adds, never erases), and advance the `watermark`. One atomic write covers all of it.
- **Fail-loud**: a corrupt store is never treated as empty; the run continues with a report caveat and refuses to overwrite (`quarantine_corrupt` can rename it aside).
- **`resurface_check(stored, new_fields, growth_pct, extra_delta_pct=None)`** (Phase 3b): `True` on a direction reversal, a growth of at least `growth_pct`% in `impact_value`, or (rolling only) a `change_pct` shift of at least `extra_delta_pct` points (`insight_rolling_report_delta_pct`) — the drift floor so a rolling reading hovering just under the growth-multiple threshold can still resurface as it drifts. No extension clause yet (deferred general Phase 4; `episode_end`/`peak_z` are persisted on `daily` records purely as scaffolding for it).
- Offline-tested by `scripts/replay_novelty_filter.py` (story_key stability/normalization, suppression, per-level caps, merge, corrupt/disabled paths, `commit_run` observed-vs-reported + monotonic guard, rolling unknown/transition/resurface/suppressed/unavailable, single story-key authority) — no auth/LLM.

### Temporal (period) level (Phase 2 — "what changed within the period")

A validated **sub-annual** cascade level sits between high-level and daily. Enabled by `insight_temporal_enabled` (default true).

- **Grain gate** (`insight_temporal.py`, above): judges each axis using the **metadata primary value metric** (not the largest numeric column), rejecting load/posting-date axes (a single bucket over `insight_temporal_batch_share` of that metric). It **detects the grain** (month/week/quarter/period), **excludes null members**, **reconciles** the series against the scanned grand total, honours a forced column (`insight_temporal_grain_column`), caps live probes (`insight_temporal_max_probes`), and tries alternative time dimensions before self-disabling. Verdict + checks in `insight_temporal_verdict.json`.
- **Drill (WHERE)**: for the single worst-declining period it runs **one bounded probe** breaking that period down by the metadata **primary dimension** (never hardcoded), attached to the period story ("October's decline concentrated in LED TV"). Stored in `insight_temporal_drill` and also surfaced to the synthesizer. Toggle `insight_period_drill`.
- **Detection** (`insight_stat_detector.period`, runs only on a `period_series` table): emits the top `insight_period_top_movers` **`period_change_contribution`** candidates with a **reconciled %** of the total change ("October -1.7M, 37% of the change") and **humanized labels** ("October", raw value kept as the fingerprint anchor). It also flags temporal patterns — **`period_sustained_decline`/`_growth`** (a consecutive run, enriched with its steepest months + the drill), **`period_reversal`**, and **`period_value_volume_divergence`** (value falls while a volume driver rises). Each finding keeps the RAW period value as its `anchor` so a new period is a new story. The existing `trend()` also runs on the series (slope + change-point) but is **skipped on gated batch-date tables**.
- **Cascade & memory**: the novelty filter tags these the `period` level (from the `period_series` coverage_kind), caps them separately (`insight_candidates_period`), and the signal detector ranks every level purely by materiality `score` — **there is no `_LEVEL_RANK` and never has been in code**; nothing gets priority ordering (see the `insight_signal_detector` bullet above). Period `story_key`s are **anchored to the period** (`{level:"period", …, metric, segment, anchor}`), so a new period is a new story while a re-run of the same period is suppressed. The stat detector retains its full deduplicated candidate set; only after story-key suppression does the novelty filter apply the per-level caps and the overall `insight_stat_max_candidates` shortlist cap. This ordering prevents already-reported high scorers from hiding a lower-ranked unseen story.
- **Gotcha — `UPDATED_DATE` is a load/posting date on the working model** (month-end batch: Dec-31 ≈ 9.8M vs neighbours in the thousands). Daily/weekly analysis on it is meaningless; the gate correctly disables date-grain and uses `DOC_MONTH`. A genuine business-**day** column would be needed for the recent-week/rolling-week/daily levels.

### Recent-week monitoring (Phase 3 calendar / Phase 3b rolling — "what changed last week" or "what changed over the trailing 7 days")

A validated **previous-complete-week** level (`insight_recent_week.py`, folding only — the validation/fetch it used to own now lives in `insight_business_day_source.py`, above) answers *"what was unusual during the most recently completed window?"* — a Monday–Sunday calendar week by default, or a trailing 7-day rolling window when `insight_week_mode: "rolling"` — comparing it to the previous window and a trailing ~`insight_week_history_weeks` (13) norm. Older daily data is norm-only; a finding is emitted for the **single** target window. Enabled by `insight_recent_week_enabled` (default true); rolling mode buckets in non-overlapping 7-day windows counting back from `effective_data_as_of` (never a 1-day slide, which would overlap 6/7 with its neighbor).

- **Deterministic composite candidate** (`insight_stat_detector.recent_week`, runs on a `recent_week_history` OR `recent_week_rolling_history` table — one method, `window_mode` derived from which kind matched): ONE `recent_week_movement` candidate with boolean **facets** `{week_over_week, abnormal_vs_baseline, reversal, sustained_run, value_volume_divergence}` — never six per-week rows, so one window yields one story and the LLM isn't relied on to merge. Window-relative math only: `impact_value = actual − previous`, **`impact_share = None`** (a WoW/rolling % is NOT a share of an annual total — mislabelling it "Share of change" is the bug this avoids); the delta % lives in the structured `recent_week` payload as `change_pct`. A perfectly **flat baseline** (robust z undefined) is detected on materiality alone; a **zero previous** window uses the trailing median as the % denominator. A move must clear **both** `insight_week_materiality_pct` and `insight_week_z_cutoff` (a big z on a tiny move is not reported). **For rolling mode only**, a raw structured observation is recorded EVERY run regardless of whether the move is significant (`state["insight_rolling_observation"]`) — see the `insight_stat_detector`/`insight_novelty_filter` bullets above for why and how its `story_key` gets attached.
- **Structured facts flow downstream**: `insight_signal_detector._copy_candidate_facts` copies the `recent_week` payload onto the signal (rolling reuses the SAME payload shape with `window_mode: "rolling"` inside it, not a second key) plus a top-level `change_pct`; `api_payloads.py`/`insight_tiles.py` surface it (a "Week over week" / "Vs prior 7 days" stat, a `week_kpi` tile with window-mode-aware wording) instead of a nonexistent share; the synthesizer receives `insight_recent_week_verdict` (now carrying `window_mode`) for the honest caveat.
- **Honest evidence contracts**: the `recent_week_history`/`recent_week_rolling_history` contracts stay `completeness:"partial"` with `window_complete:true` + `window_start/window_end/missing_expected_dates` (a bounded window, so evidence-assembler's `completeness=="complete"` gate is not falsely satisfied); the driver scan is `intrinsically_partial` ("largest returned drivers", never a false full reconciliation).
- **Cascade & memory**: the novelty filter tags calendar weeks `recent_week` and rolling windows `recent_week_rolling` (the more specific check runs first — see the routing gotcha above). Calendar's story_key is anchored to `week_start` (`{level:"recent_week", …, anchor:week_start}`) — a re-run of the same week is suppressed, the following completed week is a new story. **Rolling's story_key deliberately has NO anchor** (`{level:"recent_week_rolling", dataset, scope, axis, metric, segment}`) — its window shifts by one day every run, so an anchor would defeat suppression entirely; one key exists per axis+metric+segment forever, and `insight_novelty_filter`'s bespoke eligibility path (not `never_repeat`/`cooldown`) decides when it resurfaces. Neither level carries cascade priority — both compete purely on `score` in `insight_signal_detector._rank_and_cap`.
- **Gotcha — Phase 3/3b stay DISABLED on the working model** by design: `UPDATED_DATE` fails the batch/load-date test *and* the data (through 2023-12-31) is ~2.5 years stale, so the shared gate disables with `batch_load_date` / the staleness reason — both `insight_recent_week_verdict.json` and `insight_daily_verdict.json` carry it. It activates only on a model with a genuine, current business-**date** column. Offline-tested by the recent-week/rolling suite in `scripts/replay_stat_detector.py` (detection, flat-baseline, zero-previous, divergence, gate PASS/FAIL, window selection/fold, non-overlapping rolling shape, always-emitted observation) and `scripts/replay_novelty_filter.py` (story_key suppression/next-week, materiality-only ranking, per-level backfill, rolling eligibility paths) — no auth/LLM.

### Daily anomaly incidents (Phase 3b — "which exact days were abnormal")

`insight_daily.py` (above) answers *"flag an individual abnormal day, or a merged run of consecutive abnormal days, the moment it lands"* — reusing the exact same validated daily source Phase 3 already fetches, so it costs zero extra REST calls and disables/enables independently of weekly monitoring. Enabled by `insight_daily_enabled` (default true, gated the same safe way as `insight_temporal_enabled`/`insight_recent_week_enabled`).

- **Detection** (`insight_daily.flag_abnormal_days`/`merge_incidents`/`score_incident`, pure functions — the heavy lifting happens in the node, not the stat detector): each day is tested against a trailing rolling reference and, once enough prior history exists (`insight_daily_min_weekday_occurrences`), the same weekday's own history — **AND**-combined (both must pass and agree in direction; a flat reference is judged on materiality alone since its z is undefined). Consecutive same-direction abnormal days merge into one incident across a closed weekend (operating-day adjacency, not calendar-day adjacency). `score_incident` = `abs(cumulative_impact) / (abs(expected_total) + eps) * 100`, analogous to `recent_week`'s `score = abs(change_pct)`.
- **Recency filter** happens once, in `insight_daily.py`, before rows ever reach the stat detector — `episode_end > previous_cursor` (from `memory["daily_cursor"]`) OR `episode_end >= effective_data_as_of - insight_daily_recent_days`; on an axis's first-ever run there is no `previous_cursor`, so only the second clause applies (no doubled window).
- **Detection at the stat-detector layer** (`insight_stat_detector.daily`, dispatched EXCLUSIVELY for a `daily_incidents` table): one `daily_incident` candidate per already-merged incident row, carrying `metric`/`axis` explicitly (both participate in the story_key — without them every incident on the axis would collide onto one key), `episode_start`/`episode_end`/`peak_z`/`day_count`/`actual_total`/`expected_total`.
- **Cascade & memory**: tagged the `daily` level (already-existing routing, unchanged). `story_components`'s `daily` branch anchors on `episode_start` (`{level:"daily", dataset, scope, axis, metric, segment, anchor:episode_start}`, NO `period_anchor`) — a new incident is a new story, a re-run of the same incident is suppressed. `episode_end`/`peak_z` are persisted as mutable record fields but currently unused — scaffolding for the deferred general Phase-4 extension trigger, not wired to resurface anything yet.
- **Gotcha — stays DISABLED on the working model**, same underlying reason and same `insight_business_day_verdict.json` as recent-week. Offline-tested in `scripts/replay_stat_detector.py` (isolated day, multi-day merge, weekend veto via the AND-gate, sparse-history fallback, weekend-bridging merge, flat-baseline fallback, exclusive dispatch) and `scripts/replay_novelty_filter.py` (recency clauses, first-run-vs-later-run cursor behavior) — no auth/LLM.

## Two intentional deviations from the original spec

Both are config-driven and documented in `powerbi-summary-agent/README.md`:

1. **LLM provider is a three-way switch (Azure OpenAI / Anthropic / OpenAI), not a single default** — `src/tools/llm.py` and `main.py` fall back to `ai_provider: "azure_openai"`. For Azure, the `AZURE_OPENAI_DEPLOYMENT` env var routes, not the `model` config string. Always check live `config.json` + `.env` before assuming which backend a run hits.
2. **DAX execution defaults to `python` (REST), not `powershell`** — the PowerShell layer only existed to dodge the login hang. `scripts/execute_dax.ps1` still ships for `execution_mode: "powershell"`; the Python path is the fallback if it throws.

## Deployment path (container / scheduled runs)

Local `python -m src.main` and the production container are the **same graph** reached two ways. Changing anything below changes which endpoint or identity a run uses — check the live `config.json` + env before assuming.

- **`src/container_entrypoint.py` is the production entry, not `src.main`.** It materializes optional `AGENT_CONFIG_B64` / `AGENT_RULES_B64` secrets onto the ephemeral filesystem, then calls the same `src.main`. `AGENT_CONFIG_PATH` supplies a complete mounted config instead (a sibling `business_rules.md` is picked up automatically); `AGENT_CONFIG_OVERRIDES_JSON` layers non-secret tuning as one JSON object. The image deliberately ships `config.example.json` as its base and excludes `.env`, real config, business rules, outputs, token caches, and memory.
- **Two query APIs.** `powerbi_query_api` / `POWERBI_QUERY_API` = `auto` (default) keeps the legacy JSON `executeQueries` endpoint for interactive local runs and selects the Apache **Arrow** `executeDaxQueries` endpoint for managed-identity/service-principal runs; `json` / `arrow` force it. Arrow responses are decoded and wrapped in the **same internal row shape**, so every downstream node is unchanged — which also means an Arrow-path bug surfaces as ordinary bad rows, not an obvious decode error. Covered by `replay_powerbi_arrow.py` / `smoke_powerbi_arrow.py`.
- **Two auth modes.** `powerbi_auth_mode` / `POWERBI_AUTH_MODE` = `auto` (MSAL refresh cache, above) or `managed_identity` (`src/tools/azure_identity.py`; `AZURE_MANAGED_IDENTITY_CLIENT_ID` for a user-assigned identity). Optional RLS impersonation is off unless `powerbi_effective_username` / `powerbi_rls_roles` are supplied.
- **Cloud memory.** `insight_memory_storage: "azure_blob"` stores novelty state at `insightstate/<dataset-id>/memory.json`, separate from the app-facing `insightgen` container. Initialize once with `python scripts/initialize_cloud_memory.py` (uses `overwrite=False`; refuses to reset a non-empty store). Each run downloads at startup and publishes **only after** reports, API JSON, and history uploads succeed, using the startup ETag — so overlapping runs cannot silently clobber each other. The local `insight_memory/` directory is not read, copied, or deleted in cloud mode.
- **Output projection.** `src/tools/api_payloads.py` writes `outputs/api/*.json`; `azure_blob.py` uploads them (overwriting each run) while insight history is written **immutably** (`overwrite=False`) to `history/<dataset-id>/<YYYY>/<MM>/<DD>/<run-id>.json` and merged into a single root `insight_history.json` via ETag-conditional write. `ai_content_publisher.py` additionally projects validated outputs into a per-client container when `ai_content_publish_enabled` — **before** novelty memory commits, so a failed publish leaves that content eligible next run. Run ids come from `CONTAINER_APP_JOB_EXECUTION_NAME` or `INSIGHT_HISTORY_RUN_ID` so a replica retry is idempotent. Field-by-field contracts: `docs/azure-blob-output-schemas.md`.
- For Container Apps Jobs keep one replica / one completion; the process exits `0` only after reports, payloads/history, and cloud memory all complete.

## Gotchas

- **Metadata reading always uses the Python/REST executor**, regardless of `execution_mode` — planning needs metadata before the main-query executor mode applies.
- **Measure expressions are redacted over `executeQueries` but recovered via Fabric `getDefinition`.** `INFO.VIEW.MEASURES()` has an `[Expression]` column that the service returns empty via `executeQueries` (and raw `INFO.MEASURES()` is 400-blocked). Node 2 therefore enriches blank expressions from the **Fabric semantic-model definition API** (`POST /v1/workspaces/{ws}/semanticModels/{ds}/getDefinition?format=TMSL`, `powerbi_executor.fetch_measure_definitions_tmsl`): it decodes the base64 `model.bim` part and extracts **only sanitized measure fields** (name/table/expression/format_string/description/display_folder/is_hidden) — never the connection strings, M, or RLS roles also in `model.bim`. This works with the **same MSAL refresh cache** (silent second-audience token, `FABRIC_SCOPES`) — no second login. The endpoint can 202 into a long-running operation, which `_await_fabric_operation` polls. **Enrichment is best-effort and never fatal:** disabled by `fabric_definitions: false`, or on any Fabric failure, expressions stay blank and `get_measure_definition` falls back to its raw-column probe (`definition_unavailable` block). On the working dataset it fills **56/56** in ~10s. Node 2 logs how many measures ended up with definitions.
- Power BI's `executeQueries` endpoint can return **HTTP 200 with a per-query error embedded in the body** (`results[0].error`) — happens when a query hits a measure whose formula references a nonexistent object (measures aren't schema-validated until evaluated). `execute_python` reclassifies these as `"failed"`; if you touch it, preserve the check — trusting `resp.ok` alone turns real DAX errors into fabricated zero-row successes.
- A grand-totals `EVALUATE ROW(...)` packing several measures fails as a whole if any one measure throws — the repair loop gives it one rewrite chance, but there's no partial credit.
- **Never filter with `KEEPFILTERS('Table'[Col] = "value")`** in generated DAX — it reliably fails with a "single value for column cannot be determined" error against this model. The prompts direct `FILTER(SUMMARIZECOLUMNS(...), ...)` or `TREATAS` instead; keep that guidance if you edit them.
- Output files are written **per node**, so partial progress survives an early stop; `save_outputs` writes stub `.md`/`.html` for *both* reports on early stops. `save_outputs` is also the single, gated call site for `insight_memory.commit_run` (see "Cross-run insight memory") — passing `reported = signals if state.get("insight_report") else []`, since observed and reported are different things.
- **Azure Blob upload is post-run and best-effort** (`src/tools/azure_blob.py`, called from `main.py` after `write_api_payloads`): when `azure_blob_upload: true` it pushes `outputs/api/*.json` to the `azure_blob_container` (default `insightgen`), overwriting each run. Auth resolves `AZURE_STORAGE_CONNECTION_STRING` → `AZURE_STORAGE_KEY` → `DefaultAzureCredential` (AAD needs the *data-plane* 'Storage Blob Data Contributor' role — control-plane Contributor is not enough). Any failure prints a note and never fails the run.
- Windows console is cp1252: non-ASCII prints as `�` but files are UTF-8 and correct. Verify file bytes, not terminal echo.
- Prompts are external `.md` files in `prompts/` (each LLM node loads `_global_rules.md` plus its task prompt). `dax_planner_prompt.md`, `dax_generator_prompt.md`, `insight_signal_detector_prompt.md`, `insight_investigator_prompt.md`, and `insight_synthesizer_prompt.md` are loaded. Metadata reader/validator and insight scan planner/generator prompt files only narrate deterministic or compatibility components; edit their `.py` implementation instead.
- **LLM model context is structurally complete and shared.** `src/utils/model_context.py` supplies report understanding, summary planning, DAX generation/repair, and investigation with the full schema. The semantic profile, resolved scope, and shared baseline are also passed where relevant. Measure expressions remain on-demand through `get_measure_definition`.
- **Result-key normalization is collision-safe.** `clean_rows` uses a bare field name only when it is unique across the result table; same-named columns from different tables retain their table-qualified keys consistently on every row, preventing silent dictionary overwrites.
- **`config/business_rules.md` is company calculation/reporting logic, distinct from `_global_rules.md`** (permanent guardrails). Node 1 reads and snapshots it, and `business_rules_block(state)` injects it into every LLM prompt as authoritative guidance. Comparable-scope policy is additionally machine-enforced by `baseline_scope` plus `scope_validator`; other prose business rules remain prompt-level. If you add an LLM node, inject `business_rules_block` there too.
- Scope is branch-specific and enforced in `_global_rules.md`: the summary branch only describes; the insight branch may investigate but must use hedged contribution/correlation language, never asserted root cause. No forecasting/alerting anywhere, and **no emojis** (also stripped defensively in `html_report.py`).
- `html_report.render(md, title, eyebrow)` is a dependency-free markdown→styled-HTML renderer: corporate navy theme, `Key Metrics`-section `name: value` bullets become a two-column table, one nesting level of bullets supported, print + dark-mode styles. Both reports and the early-stop stubs go through it.
- `config/agent_settings.json` is **not read by any code**. Real values come from `config/config.json`, including metadata/scope controls (`metadata_scope_max_entities`, `insight_metadata_max_dimensions`), scan/gap/cache budgets (`insight_max_scan_queries`, `insight_max_gap_dimensions_per_signal`, `insight_total_gap_scan_budget`, `insight_max_investigation_rounds`, `insight_probe_max_rows`), signal caps, all `insight_stat_*` knobs, the cross-run memory knobs (`insight_memory_enabled`, `insight_memory_policy`, `insight_memory_cooldown_days`, `insight_max_new_per_run`, `insight_reporting_grain`, `insight_candidates_{high,period,daily}`), the temporal-level knobs (`insight_temporal_enabled`, `insight_temporal_batch_share`, `insight_temporal_min_periods`, `insight_temporal_recon_tolerance_pct`, `insight_temporal_max_probes`, `insight_temporal_grain_column`, `insight_period_top_movers`, `insight_period_recent_window`, `insight_period_drill`, `insight_period_drill_top`), the recent-week-level knobs (`insight_recent_week_enabled`, `insight_business_date_override`, `insight_week_max_date_probes`, `insight_week_start`, `insight_business_timezone`, `insight_week_max_data_lag_days`, `insight_week_history_weeks`, `insight_week_materiality_pct`, `insight_week_z_cutoff`, `insight_week_driver_rows`, `insight_week_mode`; `insight_candidates_weekly` doubles as both the `recent_week` and `recent_week_rolling` cap), the Phase 3b daily-anomaly knobs (`insight_daily_enabled`, `insight_daily_rolling_window`, `insight_daily_recent_days`, `insight_daily_exclude_today`, `insight_daily_z_cutoff`, `insight_daily_materiality_pct`, `insight_daily_min_weekday_occurrences`; `insight_candidates_daily` already listed above), the rolling-week resurface knobs (`insight_re_alert_growth_pct`, `insight_rolling_report_delta_pct` — the general `insight_re_alert_enabled` switch for high/period/daily is deferred, not yet read by any code), and the Azure-blob-upload knobs (`azure_blob_upload`, `azure_blob_account`, `azure_blob_container`, `azure_blob_prefix`). `max_rows_per_query` remains the broad-scan truncation heuristic.
- `main.py` hard-requires `tenant_id`/`workspace_id`/`dataset_id` and rejects `PASTE_`-prefixed values, exiting before the graph builds. `POWERBI_TENANT_ID` overrides the configured tenant. **`config/config.json` is gitignored and absent from a fresh clone** — create it from `config.example.json`. Same for `.env` and `config/business_rules.md`.
- **`main.py` and `config.example.json` disagree on several defaults** — e.g. `insight_max_signals` (5 vs 15) and `insight_max_investigation_rounds` (3 vs 9). Whichever `config.json` is actually loaded silently wins, so two environments can produce very differently-scoped runs. Read the live config before explaining a behavior difference.
- `AGENTS.md` at repo root is a mirror of this file for other tools — keep the two in sync when updating either (only the title line differs).
